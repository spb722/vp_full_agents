01

What the agent does

The VP Agent turns a plain-English telecom audience request — “Omani nationals with smartphones who recharged more than 5 OMR in the last 30 days” — into a validated PARENT_CONDITION: the Virtual Profile (VP) condition syntax executed by the downstream campaign/audience platform, for clients omantel and airtel.

It is deliberately not a deterministic rules engine. Two hard invariants, from AGENTS.md and .claude/CLAUDE.md, govern everything below:

  • 1VP condition syntax is only ever written inside the render_condition tool call — never hand-typed by the model anywhere else.
  • 2Routing, rendering, validation, and metadata lookup are deterministic tool outputs. The model owns interpretation: decomposing the request, resolving ambiguity, choosing columns/tables/operators, deciding what to retry.

Business knowledge — which column to prefer, how to phrase a clarification, what “high value” might mean — lives in skills, reviewed memory (golden cases, past production VPs), and seed metadata. It does not live in Python if branches.

02

Glossary

Start here if you're new — the rest of the document assumes these terms.

VP
Virtual Profile — the downstream platform's rule format for “which customers belong in this segment.”
PARENT_CONDITION
The actual condition string the platform executes, e.g. TOTAL_RECHARGE_30D ${operator} ${value}. Every VP is, at bottom, one of these strings — the only output this project may hand-write, and only inside render_condition.
Slot
A structured field pulled from the sentence — KPI phrase, filters, time token, operator/value, domain, aggregate intent. The agent's working model of “what was asked,” before any column or table is chosen.
KPI
Key Performance Indicator — a named metric column (recharge amount, data usage, handset type…) the platform can filter or aggregate on.
Seed
A reviewed template for a PARENT_CONDITION that already encodes the right aggregate function, null guards, and __groupby_ structure for a class of request. Rendering usually fills in a seed rather than composing from nothing.
Variant 1 / 2 / 3
Three rule shapes. 1 — single table, no join. 2 — multiple tables, filters resolved first, aggregate KPI last. 3 — a metric comparison between two explicit periods (uplift, downlift, % change).
MCP tool
A tool exposed over the Model Context Protocol. This project's own tools are namespaced mcp__vp__* and implemented in vp_agent/server.py + vp_agent/tools/*.py.
Skill
A markdown file under .claude/skills/ carrying procedural or business knowledge, loaded into context on demand rather than hard-coded.
Subagent
A separate, more narrowly-scoped SDK session the orchestrator launches mid-request — here, the verifier — with its own tool/skill restrictions and turn budget.
Hook
A deterministic Python callback wired into the SDK session (PreToolUse, PostToolUse, Stop) that runs around every tool call without going through the model.
Harness
The scaffolding — options, tools, hooks, prompt — wrapped around the LLM session so it behaves reliably. Full breakdown in §03.
ToolState
The one shared, mutable record (vp_agent/schemas.py) both hooks and the API read and write for a single request.
03

Harnesses

“Harness” means the deterministic scaffolding around an LLM session — options, tools, hooks, prompt. One runs live; three more exercise it offline, from different angles.

Four harnesses
#HarnessFilesRole
1 Orchestration
live		 orchestrator.py · hooks.py · schemas.py · server.py · settings.json Runs one Claude Agent SDK session per incoming request: extraction → retrieval → resolution → render → validate → optional verify. The harness HARNESS_FIXES.md documents fixes for.
2 Syntax-coverage audit scripts/audit_syntax_coverage.py Offline, no LLM calls. Confirms the skills under .claude/skills — the agent's only procedural memory — actually cover the syntax constructs seen in real production VPs.
3 Live agentic eval scripts/eval_agentic.py Drives the real orchestration harness against a labeled CSV of sentence → expected-condition pairs. Needed because agentic output varies run to run.
4 Baseline-vs-optimized regression scripts/compare_vp_variants.py Health-checks two live API deployments (e.g. ports 8000 / 8001, via VP_VARIANT) and runs identical cases through both, to compare a baseline build against an optimized one.

Extraction, routing, rendering, and validation are not separate harnesses — they are pipeline stages inside the one orchestration harness, driven by a single SDK session.

Entry points into the orchestration harness: CLI (vp_agent/cli.py) and API (POST /vp/build in vp_agent/api.py) both call orchestrator.run_request; both are launched via scripts/run_api.sh.

Security note

scripts/run_api.sh currently has a live-looking OAuth token committed in plaintext (plus a second, commented-out one). Rotate it and move it to an untracked env file — flagged here since it surfaced during this review, separate from the architecture write-up itself.

04

Orchestration internals

orchestrator.py

FunctionRole
ORCHESTRATOR_APPENDA large system-prompt append on top of the Claude Code preset prompt — the actual pipeline spec: two-stage skill loading, evidence-gathering rules, decision rules (filters, main KPI, snapshot vs. raw, aggregate, date bounds, ordering), record_resolution, manual template composition, render_condition, validate_rule warning discipline, verifier trigger conditions, clarification-only exit contract.
build_agents()Defines exactly one subagent, verifier (.claude/agents/verifier.md), restricted to Skill, Read, mcp__vp__retrieve_existing_vps, mcp__vp__validate_rule, plus skill vp-metrics-comparison only, maxTurns=5. Deliberately denied the orchestrator's own skills so it re-derives the answer independently rather than restating the author's reasoning.
build_options()Builds ClaudeAgentOptions: base tools=["Skill","Read","Agent"] (narrowed on purpose — see §07), the 12 mcp__vp__* tools via allowed_tools, disallowed_tools=["Bash"], skills="all", hooks, max_turns=25 by default.
run_request()Stores the real request/client on shared state — so hooks validate against what the user actually asked, not whatever the model echoes back — then streams one ClaudeSDKClient session.

hooks.py — the enforcement layer

PreToolUse gate

  • Marks slots resolved once normalize_slots / retrieve_columns / record_resolution has run.
  • Denies render_condition until slots are resolved.
  • ToolSearch loop-breaker: denies a repeated schema search for a tool already available, with an explicit “stop searching, call it directly” message.
  • Denies Agent (verifier launch) until a rule exists; caps any subagent to 3 launches per request.

PostToolUse audit

  • Records every call/response into the shared trace and structured ToolState fields.
  • After retrieve_columns: soft warning if a request word never reached any submitted role.
  • After render_condition: immediately runs validate_rule against the real stored request; hard-blocks on errors, surfaces warnings + seed-clause regressions as must-address context.
  • Flags (never trusts) a non-render_condition output that tries to smuggle a parent_condition.

Stop backstop

  • Fires at most once per request.
  • If the run is ending with no rendered condition, blocks — forcing either completion or exactly one Clarification question: … line.
  • A run can never silently end with nothing.

schemas.py — ToolState

A single mutable object shared across the whole request: request/client, slot/render progress flags, resolution, selected seed, validation result, verifier verdict, retrieval/seed audit ids, subagent launch counts, and the full tool-call trace — the audit backbone both hooks and the API read from.

05

MCP tool reference

Every capability the model has, beyond reading skills and launching the verifier. Each tool wraps a pure-Python function that does no business reasoning — it executes a deterministic lookup or computation and hands evidence back. render_condition is highlighted: it's the one tool allowed to emit syntax.

12 tools · vp_agent/server.py
ToolModuleWhat it does
normalize_slotstools/normalize.pyRegex first pass. Returns only mechanical fields — operator, value, time token, filters. Withholds domain/kpi_phrase/aggregate/negation, which require judgment.
retrieve_columnstools/retrieve.pyMain retrieval call, one batch across metric + filter + time roles. Hybrid rank: 0.5 × BM25-normalized + 0.5 × embedding-normalized char-3-gram cosine, plus metadata/time-window/client-prior tiebreakers. Returns top 5 per role with observed values, production usage, adaptation notes, unexplained terms. Supports paging (page 2/3) on the same audit_id for a genuinely unresolved role.
retrieve_existing_vpstools/retrieve_vps.pyRanks previously-approved client VPs by token coverage, name precision, semantic similarity — finds reusable helper VPs, especially both operands of a Variant-3 comparison.
record_resolutionserver.py (inline)Pure audit record of the agent's semantic decision — no logic of its own. Flips the slots_seen gate.
shelf_lookuptools/shelf.pyChecks whether a single KPI/time-token pair has a precomputed 360 Profile “shelf” KPI.
route_tabletools/router.pyDeterministically routes a domain/token (+ optional KPI group) to a source table. Legacy/compatibility — not in the live allowed_tools; table choice in the live path comes from the retrieved KPI's own group_name instead.
select_seedtools/seed.pyScores seed-catalog entries on client, time axis, KPI-axis phrase match, aggregate intent, 360-vs-raw preference. Returns one proposed seed + up to 3 diverse alternatives; flags a weak/one-survivor field via supply.advisory.
build_condition_plantools/plan.pyAssembles deterministic render_condition input from slots/columns/route/seed. Legacy/compatibility — not part of the live orchestrator path.
render_conditiontools/render.pyThe only legal emitter of PARENT_CONDITION syntax. Renders the final string from a seed/template, variables, and resolved filters — everything upstream exists to feed this one call correctly.
validate_ruletools/validate.pyStructural + semantic check: placeholder discipline, known columns, groupby ordering, unrendered stated numbers, intent cues missing from the rule, shape differences vs. existing production VPs on the same column.
episodic_lookuptools/memory.pyLooks up reviewed prior human corrections for similar slots/client — a memory surface for recurring mistakes.
queue_correctiontools/memory.pyQueues a marketer/verifier correction for human review before it's trusted as reinforcement.

Skills

Skills are the agent's procedural/business memory — markdown files whose frontmatter description doubles as the trigger condition shown to the model.

7 skills · .claude/skills/
SkillPurposeTriggered when
vp-extractionAlways loaded first. Parses the request into slots: KPI phrase, filters as predicates (comparison / IN LIST / NOT IN LIST / range / null-presence / pattern), time token, operator/value, domain, aggregate intent, Variant-3 comparison object, clarification discipline.Every new request, or re-extraction after a coverage failure.
vp-rendering-rulesAlways loaded first. The emission contract for render_condition: compose the full template yourself, placeholder placement rules, __groupby_ syntax, how to read validation warnings, snapshot vs. event date-bound rules.Immediately before rendering, and when interpreting validation failures.
vp-table-routingChooses among 360 Profile, summarized/event, profile, recharge, subscriptions, lifecycle, audience-segment tables; multi-table ordering rule.After retrieval, before column resolution, when more than one table is plausible.
vp-variant-selectionDefines Variant 1/2/3 and the seed-selection procedure.Rule spans multiple tables, or uses metric/uplift/downlift language.
vp-disambiguationGoverns when and how to ask one batched, plain-English clarification. Forbids exposing internal column/table/seed names.Low candidate confidence, multiple KPI matches, missing required time window, uncertain Variant-3 base.
vp-metrics-comparisonThe reviewed convention for Variant-3 period comparisons: extract both period roles, reuse existing helper VPs by exact name, apply the “Rakesh KT” percentage-decline formula, semantic-verification checklist.Explicit period comparison / uplift / downlift / decline / % change / growth / ratio. Also the only skill the verifier may load.
vp-golden-examplesReviewed example memory from the UI golden-case dataset: resolver workflow (compare candidates to golden patterns) and verifier workflow (confirm KPI family; snapshot KPIs shouldn't get an added event-date condition).Retrieval returns multiple plausible KPI families, or choosing Customer-360-snapshot vs. event-table-with-date-bounds.

Supporting, non-skill files: .claude/agents/verifier.md — the verifier's own prompt, deliberately withheld from the orchestrator's skills (except vp-metrics-comparison) so it reasons independently, always ending with exactly one VERDICT: pass|retry|ask — <reason> line. .claude/settings.json — permission allowlist: Skill, Read, Agent, mcp__vp__* allowed; Bash denied.

End-to-end flow

flowchart TD
    A[POST /vp/build] --> B[orchestrator.run_request]
    B --> C[Load skills: vp-extraction + vp-rendering-rules]
    C --> D{Trigger conditions met?}
    D -->|yes| E[Load vp-disambiguation / vp-variant-selection /\nvp-metrics-comparison / vp-table-routing / vp-golden-examples]
    D -->|no| F
    E --> F[normalize_slots]
    F --> G[retrieve_columns]
    G --> H{aggregate / formula /\nguard / groupby needed?}
    H -->|yes| I[select_seed]
    H -->|no| J
    I --> J{Variant 3?}
    J -->|yes| K[retrieve_existing_vps per period]
    J -->|no| L
    K --> L[Agent reasons: main KPI, filters,\nsnapshot vs raw, aggregate fn,\ndate bounds, table]
    L --> M[record_resolution]
    M --> N[Agent composes full PARENT_CONDITION]
    N --> O[render_condition]
    O --> P[validate_rule]
    P --> Q{Verifier triggers?\nVariant 3 / unresolved warnings /\nweak seed / unexplained terms}
    Q -->|yes| R[Agent launches verifier subagent]
    Q -->|no| S[Build VPBuildResponse]
    R --> T{VERDICT}
    T -->|retry| N
    T -->|ask| U[Clarification question]
    T -->|pass| S
    S --> V[Client receives JSON]
    U --> V
Key gating detail

The orchestrator's base tool list is deliberately narrowed to Skill, Read, Agent rather than left as Claude Code's full built-in set. Left unset, and stacked with the 12 mcp__vp__* tools, every tool schema got pushed behind ToolSearch — a weaker model got stuck repeatedly searching without ever calling. Narrowing the base set was the single most consequential harness fix recorded in HARNESS_FIXES.md.

API contract

POST /vp/build · vp_agent/api.py

Request

{
  "client": "omantel",
  "sentence": "Omani nationals with smartphones who recharged more than 5 OMR in the last 30 days",
  "request_id": "optional-caller-supplied-id",
  "session_id": "optional",
  "user_id": "optional"
}

Response — key fields

{
  "ok": true,
  "mode": "agent",
  "orchestrator_model": "claude-sonnet-5",
  "subagent_model": "claude-haiku-4-5-20251001",
  "parent_condition": "TOTAL_RECHARGE_30D ${operator} ${value}",
  "selected_columns": ["TOTAL_RECHARGE_30D", "NATIONALITY", "DEVICE_TYPE"],
  "selected_vps": [],
  "seed": "seed_id_used",
  "snapshot": false,
  "slots": { "…": "normalized slots" },
  "validation": { "errors": [], "warnings": [] },
  "verifier_verdict": { "decision": "pass", "reason": "…" },
  "needs_clarification": false,
  "clarification_question": null,
  "warnings": []
}

If the agent can't produce a rule: ok=false, parent_condition=null, and either needs_clarification=true with a question, or a failure_reason plus diagnostics naming exactly which tools ran and why extraction from the transcript failed. _build_agentic never lets the caller receive a silently empty success.

GET /health and GET /observability (Langfuse status, active variant) are also exposed for operational checks.

Worked example

“Omani nationals with smartphones who recharged more than 5 OMR in the last 30 days,” client omantel.

  1. Skills load — vp-extraction, vp-rendering-rules always; vp-table-routing too, since recharge vs. profile tables are both plausible.
  2. normalize_slots — mechanical fields only: operator: ">", value: 5, time_token: "CurrentTime-30DAYS". KPI phrase, domain, and the two filters are left for the model.
  3. retrieve_columns (one batched call) — top candidates per role: a recharge-amount metric column, a nationality filter column, a device-type filter column, each with observed values and production usage counts.
  4. Model reasons — main KPI = recharge amount aggregate; filters = nationality "Oman", device type "Smartphone"; window = rolling 30 days (not a completed month) → CurrentTime-30DAYS; table = the recharge KPI's own group_name.
  5. select_seed (aggregate + time window needed) — proposes a seed for “aggregate metric over rolling N days, subscriber-level.”
  6. record_resolution — audit record of the decision above; flips slots_seen = True, unlocking render_condition.
  7. render_condition — model composes the full template by hand, emits TOTAL_RECHARGE_30D ${operator} ${value} with the filters folded in. The PostToolUse hook immediately runs validate_rule against the real sentence — no errors; a coverage warning would only fire if “5 OMR” never reached a placeholder, and here it does.
  8. validate_rule — the model's own closing check: clean.
  9. Verifier check — no Variant-3 language, no unresolved warnings, no weak seed signal verifier not required — the model finishes directly.
  10. Stop hook — sees render_seen = True, does nothing.
  11. Response — api.py extracts parent_condition from ToolState, returns ok: true.
If “high-value customers” had been the ask instead

Step 4 fails to resolve which threshold "high-value" means. vp-disambiguation triggers one batched clarification — e.g. “By 'high-value', do you mean total recharge above a specific amount, or top-tier tariff plan customers?” — instead of a guessed rule. The Stop hook requires at least one retrieval call to have run first, so the agent must check whether “high-value” already resolves cleanly before asking.

10

Edge-case handling

Retry classes — AGENTS.md

FailureResponse
Column / coverageRe-call retrieve_columns with the failed column added to exclude.
Routing / dateRe-derive the table from the retrieved KPI's group, with corrected slots.
Render / grammarTreated as a code bug, never hand-patched — must re-emit through render_condition.
AmbiguityExactly one batched, plain-English clarification question, no internal names exposed.

Data question vs. intent question

vp-disambiguation draws one line: a data question is answerable via retrieve_columns / retrieve_existing_vps and is never asked of the user. An intent question is genuinely ambiguous between two equally-supported readings — the only kind allowed to reach the user. The Stop hook enforces that no clarification is issued before at least one retrieval call has actually run.

Layered validation

LayerChecks
1 · render-timeHook, immediately after render_condition. Hard errors block; warnings and seed-clause regressions (a dropped null guard, __groupby_, or aggregate function) surface as must-address context, checked against the real stored request.
2 · validate_ruleAgent-invoked closing step. Structural errors (placeholder count/adjacency, groupby ordering, unknown columns) plus three advisory classes: coverage (a stated number never rendered), intent (negation / per-entity / average / alternation / category-value / scope cues absent from the rule), convention (a same-column production VP uses a different shape).
3 · verifierConditional, independent second opinion — triggered deterministically, never by the model's own confidence — for Variant-3 comparisons, unresolved warnings, a weak seed, or unexplained retrieval terms. Ends with one VERDICT line; retry sends the agent back to re-render and re-validate, ask forces a clarification instead of a rule.
4 · Stop backstopGuarantees a run can never silently end with neither a rule nor a clarification.

Retrieval-time edge cases are handled by surfacing evidence rather than dropping it: weaker candidates keep visible adaptation notes instead of being deleted, unexplained_terms flags a filter phrase that may need splitting, production_uses breaks ties between columns sharing identical metadata, and unaddressed_request_terms catches a whole phrase that never became a role at all.

11

How the loop works

There is no bespoke while loop in this codebase. The loop is the Claude Agent SDK's own agentic turn loop — tool call ⇄ model reasoning, up to max_turns = 25. The harness's job is to shape that loop via hooks and prompt, not replace it.

LoopMechanism
Turn loopClaudeSDKClient.query() + receive_response() streams messages; the model chooses each tool call; PreToolUse/PostToolUse fire around every call; ends on final text or at max_turns.
Gating loopPreToolUse blocks premature render_condition and premature verifier launch; breaks a ToolSearch fetch-without-call stall after one grace retry.
Evidence/audit loopPostToolUse folds every structured output into shared state, and select roles get one-shot warning injections the model must react to next turn — closing the loop on silent omissions without hard-blocking an in-progress chain.
Termination loopStop hook fires at most once per request — one corrective turn, never an infinite spin.
Verify-and-retry sub-loopretry verdict → revise → re-render → re-validate → optionally re-verify, bounded by max_turns, the subagent's own maxTurns=5, and a 3-launches-per-agent cap.
Pagination "loop"retrieve_columns / select_seed return top 5 by default; the model may fetch further pages of the same audit only for a genuinely unresolved role — bounded, explicitly gated, not a free retry.

State-machine view of the gates

stateDiagram-v2
    [*] --> SlotsUnresolved
    SlotsUnresolved --> SlotsResolved: normalize_slots / retrieve_columns / record_resolution
    SlotsResolved --> RenderBlocked: render_condition attempted early (denied)
    SlotsResolved --> RuleRendered: render_condition succeeds, no errors
    RuleRendered --> VerifierOptional: verifier not required
    RuleRendered --> VerifierRequired: Variant 3 / warnings / weak seed / unexplained terms
    VerifierRequired --> RuleRendered: VERDICT retry
    VerifierRequired --> Finished: VERDICT pass or ask
    VerifierOptional --> Finished
    SlotsResolved --> Finished: Stop hook forces one clarification if no rule was ever rendered
    Finished --> [*]
